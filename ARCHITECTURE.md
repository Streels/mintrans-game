# Архитектура «Минтранса»

Главная цель — **модульность**: новую механику добавляют новым модулем, новым правилом или новыми данными, а не переписыванием готового кода.

## Модули и зависимости

```
content/ ─(JSON)─► Mintrans.Data ─► Mintrans.Simulation ─► Mintrans.World ─► Mintrans.Core
                         ▲                 ▲                  ▲
                         └──────── game/ (Godot: отображение и ввод) ──────┘
```

| Модуль | Что внутри | От чего зависит |
| --- | --- | --- |
| `src/Mintrans.Core` | Базовые типы: клетка `GridPos`, 4 стороны клетки, `GridRect`, идентификаторы `TypeId` и `SiteId`. | ни от чего |
| `src/Mintrans.World` | Карта: слои клеток, рельеф с расширяемыми категориями, транспортные сети (дороги, рельсы), площадки объектов из частей и правила их размещения. | Core |
| `src/Mintrans.Simulation` | Игровое время (шаг = час), конвейер систем по фазам и расписанию, очередь команд игрока, регулятор скорости и паузы. | Core, World |
| `src/Mintrans.Construction` | Строительство игроком: план и постройка путей, дорог, станций, снос. Правила клеток — отдельные классы `INetworkCellRule`. | Core, World |
| `src/Mintrans.Data` | Чтение `content/`: каталоги, карты и настройки темпа из JSON, операции построения карты. | Core, World, Simulation, Construction |
| `game/` | Godot: изометрия, отрисовка, камера, интерфейс. Ничего не решает за симуляцию. | Core, World, Data |
| `tests/*` | xUnit-тесты: по проекту тестов на каждый модуль. | тестируемый модуль |

Будущие модули добавляются рядом и тоже зависят только от нижних слоёв: `Mintrans.Economy` (ресурсы, предприятия, города) и `Mintrans.Transport` (граф сети, техника, маршруты). Оба подключаются к симуляции своими системами (`ISimulationSystem`) и данными (`SimulationState.Add`), не меняя её. Модули **не ссылаются друг на друга по кругу**; Godot-код **никогда** не попадает в `src/`.

## Правила, которые держат модульность

1. **Типы задаются данными.** Виды поверхности, сети, типы объектов — строки `TypeId` из `content/`. Новый вид — новая запись в JSON, а не новый `enum`.
2. **Расширение через регистрацию.** Шаги построения карты (`IMapOperation`) и правила размещения (`IPlacementRule`) — отдельные классы в списке. Новое поведение = новый класс + одна строка регистрации.
3. **Карта не знает о других модулях.** Объект на карте — только тип, имя и клетки. Экономика и транспорт хранят свои данные отдельно и связывают их по `SiteId`.
4. **Данные в плотных массивах.** Слои карты — `CellLayer<T>` (один массив на слой). Это быстро и удобно для будущей многопоточности.
5. **Изображение отделено от логики.** Изометрия живёт только в `game/scripts/View/IsoProjection.cs`. Цвета и названия — в `game/styles/`, на правила они не влияют.
6. **Воспроизводимость.** Одинаковые данные и семя дают одинаковый мир; это проверяет тест.
7. **Понятные ошибки данных.** Ошибка в JSON сообщает файл и путь внутри него: `maps/prototype.json → terrain[3].radius`.

## Файлы данных

| Файл | Что описывает |
| --- | --- |
| `content/world/terrain.json` | Природные категории (поверхность, растительность, вода, месторождения) и их виды. |
| `content/world/networks.json` | Типы транспортных сетей. |
| `content/simulation.json` | Темп: секунд на игровой час при 1×, набор скоростей, предел шагов за кадр. |
| `content/construction.json` | Что и где можно строить: запрещённая природа, разрешённые площадки для сетей, виды станций. |
| `content/maps/*.json` | Карты: размер, семя, шаги рельефа, готовые участки сетей, объекты. |
| `game/styles/map_style.json` | Цвета карты: как смешивать слои, сети, площадки объектов. |
| `game/styles/names.ru.json` | Русские названия идентификаторов для интерфейса. |

Формат данных предварительный: его утвердим в теме 16 «Сохранения и данные игры».

## Команды

Запуск, редактор и тесты — скрипты в корне, см. [README.md](README.md). Напрямую:

```bash
dotnet test Mintrans.slnx
```

Параметры игры после `--`: `--map=prototype`, `--focus=city --zoom=2`, `--screenshot=файл.png`, `--content=путь`.

## Время и порядок расчётов

- Один вызов `GameSimulation.Step()` — один игровой час. Сначала применяются накопленные команды игрока, затем системы, которым пора работать, по возрастанию фазы: перевозки (`Transport`) → производство (`Production`) → потребление (`Consumption`) → рост → статистика (`Statistics`).
- Расписание системы — период в часах: `Hourly`, `Daily` (на границе суток, после перевозок последнего часа), `Weekly`. Квартал появится вместе с календарём (тема 14).
- Действия игрока — команды (`IGameCommand`) в очереди; они вступают в силу со следующего шага.
- `SimulationRunner` переводит реальные секунды в шаги. Скорость меняет только частоту шагов, поэтому результат зависит лишь от числа прошедших часов (это проверяет тест).

## Строительство

- `Builder` сначала строит план (`PlanPath`, `PlanStation`, `PlanDemolish`) — по нему интерфейс подсвечивает клетки и показывает причину отказа, — затем строит тот же план. Без плана без проблем карта не меняется.
- Стройка выполняется между шагами симуляции, поэтому действует со следующего игрового часа (docs/03).
- Инструменты в Godot (`game/scripts/Tools`) — тонкие обёртки над `Builder`; новый инструмент — класс `IBuildTool` и строка в `BuildTools.Create`.
- Концы прокладываемого пути пристыковываются к уже лежащей сети в своей или соседней клетке (как в OpenTTD).

## Сети и площадки

- Клетки связаны только через стороны (4 соседа). Диагональ — лесенка клеток с угловыми кусками пути, как в OpenTTD.
- Раскладка сети задаётся в `networks.json`: `edges` (дорога: все стороны в клетке соединены) или `tracks` (рельсы: прямые и угловые куски). Новая раскладка — новый наследник `NetworkLayer` и строка в `NetworkLayouts`.
- Площадка объекта — объединение прямоугольных частей: базовая область плюс присоединённые части (модули, станции). Каждая часть примыкает к площадке стороной клетки, поэтому форма может быть непрямоугольной.
