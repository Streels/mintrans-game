# 02в. Контракт пространственного движка v1: геометрия, клетки, чанки

**Статус:** согласованная спецификация для начала реализации (31.10.2026). Это **целевая архитектура**, а не описание уже написанного движка. Размер карты, стоимость строительства и масштаб игрового времени здесь намеренно не выбираются.

## 1. Главный инвариант

**Истина — геометрия объектов в мировых координатах. Занятость клеток — производный пространственный индекс, а не исходная геометрия.**

- Вся карта использует единую систему мировых координат **в метрах**; вычисления геометрии — `double`.
- Квадратная строительная клетка имеет шаг **5×5 м**. Начало координат сетки одинаково для каждого чанка и каждого объекта; клетки не имеют локальных смещений.
- Строительная сетка — дискретная **система адресации** и удобного размещения, а не требование проводить каждую дугу рельсов через центр клетки.
- Рельсы и другие линейные объекты хранят исходную метрическую геометрию. Здания и площадки используют собственные метрические footprints, которые могут быть выровнены по клеткам.
- Нельзя считать клетку «одним объектом»: в одну клетку могут попадать два **неконфликтующих** габарита. Индекс возвращает **всех кандидатов**, а окончательное пересечение проверяется по геометрии и высотному уровню.

## 2. Преобразование координат и числовая точность

- `CellSizeM = 5.0`.
- Мировая точка `(x,y)` соответствует `GridPos(floor(x/5), floor(y/5))`. Использовать **математический floor**, а не приведение `double` к `int` (важно на отрицательных координатах).
- Полуоткрытый квадрат клетки `(cx,cy)`: `[5*cx, 5*(cx+1)) × [5*cy,5*(cy+1))`; граничные касания учитываются геометрическим допуском.
- `GridPos` хранит адрес, `WorldPoint` — метрическое положение, `WorldGeometry` — исходные отрезки, дуги или контуры. Не округлять мировые точки при сохранении и построении графа.
- Использовать общий геометрический `epsilon` для сравнения мировых точек (стартовый ориентир `1e-4 м`, конфигурируемый); не применять произвольное округление для восстановления связности.
- Проверка границ мира выполняется в **метрах**, а не длиной массивов `Width×Height`. Фактические размеры карты выберем позже.

### Предлагаемые модели C#

```csharp
public readonly record struct WorldPoint(double X, double Y);
public readonly record struct GridPos(int X, int Y);
public readonly record struct ChunkPos(int X, int Y);
public readonly record struct CellKey(int X, int Y, int Level);
public readonly record struct WorldBounds(double MinX, double MinY, double MaxX, double MaxY);

public static class SpatialScale
{
    public const double CellM = 5.0;
    public const int ChunkCells = 64; // стартовое внутреннее значение, менять без изменения игровых правил

    public static GridPos ToCell(WorldPoint p) =>
        new((int)Math.Floor(p.X / CellM), (int)Math.Floor(p.Y / CellM));

    public static ChunkPos ToChunk(GridPos p) =>
        new((int)Math.Floor((double)p.X / ChunkCells),
            (int)Math.Floor((double)p.Y / ChunkCells));
}
```

64×64 клетки = 320×320 м на один **индексный чанк**. Это предлагаемый технический размер по умолчанию, **не физический размер игрового региона** и не требование хранить 4096 пустых записей внутри чанка. Для рельефа допустима отдельная сетка/размер чанка.

## 3. Разреженный индекс занятости

Предлагаемое представление: `Dictionary<ChunkPos, SparseChunk>`, где каждый `SparseChunk` хранит `Dictionary<LocalCell, Set<ObjectId>>` только для ячеек, затронутых геометрией. Пустые чанки и пустые записи удаляются. Отдельно храним исходную геометрию: `ObjectId → Geometry + Level + metadata`.

### Как получить занятые клетки

1. На входе исходная геометрия объекта и его **физический габарит**: например, swept-corridor рельсового пути, ширина сооружения или footprint здания. Для рельсов использовать ось с ненулевым расширением до габарита, а не тонкую линию без толщины.
2. Получить AABB физической геометрии и список строительных клеток, пересекающих AABB.
3. Применить точный тест `GeometryIntersectsCell` с указанным габаритом. Добавить ID объекта в каждую пересечённую клетку. Кривая может затронуть несколько клеток по обе стороны оси.
4. При строительной проверке выполнить запрос по этим клеткам к **кандидатам**, затем провести **точный тест `GeometryConflicts(objectA,objectB,level)`**. Два объекта могут числиться в одной клетке, но не пересекаться физическими контурами.
5. Разрешённые сочетания (например, железнодорожный переезд с дорогой или пересечение на разных высотных уровнях) определяет **явное правило инфраструктуры**, а не общее «клетка занята — отказ».
6. Не хранить набор клеток как единственный источник истины. После изменения геометрии индекс должен быть полностью восстанавливаем из исходных объектов; сохранение производного индекса необязательно.

### Инварианты пересечений

- При двух параллельных путях с осями через 5 м **проверять контуры**, а не запрещать любые две записи в одной клетке.
- Для проверки коллизий различать объекты строительства и подвижную занятость поездом. Подвижная занятость — отдельный слой физической длины поезда и резерваций в транспортном графе.
- Для железной дороги при построении учитывать габарит коридора и явную зону стрелочного узла; точные динамические габариты на кривых можно параметризовать позже.
- На разных высотах геометрическое пересечение в X/Y само по себе не означает конфликт, но **разрешение пересечения требует явного типа моста/тоннеля и проверки просвета**; значение просвета уточняется отдельно.

## 4. Построение, изменение и откат

**Геометрия первична в каждой транзакции:**
`Input → PreviewGeometry → ComputeTouchedCells → TerrainCheck → ExactConflictCheck → ValidateTransport → CommitGeometryAndIndices → InvalidateAffectedGraphAndView`.

- Предпросмотр создаёт временную геометрию и временный набор клеток, **не мутирует** мир.
- Подтверждение проверяет актуальную ревизию мира, местность, существующие объекты, занятость и бронирование поездов.
- Изменение существующего объекта удаляет **старые** ссылки `ObjectId` из индекса и добавляет **новые** по вновь вычисленным клеткам; сетка не решает, как изменить геометрию.
- Геометрия, индекс, связность транспортной сети и связанные сооружения изменяются **атомарно**; при отказе либо откатываются, либо остаются без изменений.
- Инвалидировать только затронутые чанки отображения, строительные запросы и участки транспортного графа. Полный проход по миру на каждый клик запрещён.
- В мультиобъектной клетке индексу нужна стабильная ссылка на объект и уровень, а не один флаг `Occupied`.

## 5. Местность: отдельный пространственный слой

- Рельеф (высота, тип поверхности, вода, лес, месторождение) хранится отдельно от строительной занятости; допустимы крупные ячейки, поля высот, чанки или процедурный генератор.
- При размещении любого объекта запросить `SampleTerrain(WorldPoint)` и/или высотный профиль вдоль его footprint; **не предполагать плоскую местность из-за отсутствия строительных клеток**.
- Семя генерации и настройки дают воспроизводимый рельеф независимо от последовательности загрузки чанков.
- При возведении инфраструктуры сохранить необходимые изменения поверхности/насыпи отдельно, чтобы повторная генерация чанка не уничтожила постройку.
- Высотные отметки и ограничения уклонов принадлежат физической модели объекта. Численный уклон, допустимый для ж/д, пока отдельный баланс, но API проверки должен принимать его сразу.

## 6. Изометрия и работа камеры

- Обычное отображение карты — **без клетчатой разметки**.
- В режиме строительства показывать **только видимую часть единой глобальной сетки**, плюс предварительный footprint под курсором и препятствия/причины невозможности размещения.
- Рендер подгружает/обновляет только видимые или близлежащие чанки, использует отсечение по камере и уровни детализации; при дальнем масштабе можно не отображать отдельные 5-метровые линии, чтобы не превращать карту в шум.
- Преобразования `World→IsometricScreen` и обратный выбор точки в мире не меняют геометрию. Сетка привязана к **мировым**, а не экранным координатам.
- Просмотр карты и отрисовка должны работать, когда строительный чанк ещё не создан.

## 7. Отдельный железнодорожный граф

Рельсовые примитивы и узлы графа хранят точные метрические длины, направления и точки соединения. Сеточный индекс нужен для выбора объекта, строительства и столкновений; **не превращать 5-метровые клетки в вершины поиска маршрута**. Резервации и сигналы привязаны к физическим сегментам/координатам. Механика кривых и стрелок описана в [10в](10c_rail_editor_spec.md).

## 8. Новые форматы и политика старых данных

- **Сохранений игроков, которые требуется поддерживать, ещё нет.** Совместимость старых игровых сохранений и миграцию сетки «как было → 5 м» **не реализуем**.
- Для нового формата сразу можно предусмотреть `schemaVersion`, `cellSizeM=5` и метрическую геометрию; сериализация должна быть детерминированной.
- **Исходные карты, тестовые fixtures и описания прототипа в репозитории — это не сохранения игроков.** Их следует обновить под новые размеры/форматы, чтобы не сломать тестовый сценарий.
- Не интерпретировать старые значения `GridPos` как физические метры без осознанного пересчёта в обновляемых тестовых картах.

## 9. Достаточные критерии готовности пространственного ядра

1. `ToCell` корректен на границах клеток и отрицательных координатах; у чанков общая мировая привязка.
2. В пустом мире не выделяются миллионы строительных клеток; стройка 1 км линии создаёт записи только вдоль её коридора.
3. Кривая, идущая не через центры клеток, помечает все реально затронутые клетки и ни одна её часть не пропадает на границе чанка.
4. Два объекта попадают в одну индексную клетку без ошибочной коллизии, когда реальные габариты не пересекаются.
5. Изменение радиуса и последующая отмена не меняют реальный индекс. При подтверждении старые ссылки удаляются, новые вставляются.
6. Удаление объекта очищает пустые локальные клетки и чанки; исходная геометрия не искажается.
7. Рельеф и запреты на строительство корректно читаются в области, где никогда не существовало строительных клеток.
8. Камера и режим строительства не материализуют всю карту; вдалеке мелкая разметка скрывается.
9. Строительство не изменяет маршрутный граф, когда предпросмотр не подтверждён; после подтверждения пересчитываются только затронутые связности.
10. Новые тестовые карты загружаются; нет зависимости от поддержки старых игровых сохранений.

## 10. Что остаётся отдельными задачами

**Не блокирует начало программирования пространственного ядра:** размер тестовой и полной карты (в километрах), темп игровых часов, экономическая стоимость, точные характеристики насыпей, уклонов и высотных габаритов мостов, а также оптимизация на реальном профиле производительности. Эти параметры не меняют принятое правило «геометрия первична, клетки — производный индекс».
